# Plus One：决策记录

这份文档记录和 Claude 讨论 Plus One 时做过的关键决定。按时间顺序写，每条说明四件事：问题是什么、考虑过哪些方案、最后怎么定、为什么这么定。被推翻或撤回的方案也保留，免得以后重复走弯路。

每个版本具体改了什么，见 `HANDOFF.md` 的迭代历史表和 `docs/CHANGES-SINCE-FIGMA.md`。

---

## 一、定位与研究

### D1. 卖点与真实需求（用户研究 → PPT）
- **问题**：Plus One 到底卖什么，用户的真实需求是什么？
- **做法**：用户研究结论整理成文档，再扩展成 42 页 PPT（`deck/`）。深度研究报告和笔记放在 `research/`。
- **关键结论**：
  - 信任比价格更重要。用户原话里，“被骗 / 分不清真假票”出现 19 次，“手续费太贵”只有 4 次。
  - 一个人去演出是真实的痛点。
  - 放鸽子是找搭子最大的风险。
  - 小组比一对一更好。
  - 女性对安全的需求更强。
- **图表风格**：研究 PPT 的图表统一为黑白灰，按 dataviz 规范重做过一次。

### D2. 研究发现的 8 个缺口，先在 demo 里补上（M7）
- 包括押金与签到、集合点、安全面板、女性专属小队需要身份认证、举报与拉黑、到场记录、固定 $2 手续费、锁票演出只走官方渠道、分摊付款、Re-crew（同一队人再约下一场）。

### D3. 竞品压力：找搭子和面值票单独都不是壁垒（M8 前）
- **问题**：Radiate、ConcertBuddy 已经能找搭子；Ticketmaster 和 CashorTrade 已经合作做面值转售。我们还有什么优势？
- **决定**：差异化放在“一定会一起到场的小队”：
  - 持票身份；
  - 到场记录，这是会不断积累的数据；
  - 小队而不是一对一配对；
  - 多余的票优先给小队里的人；
  - 小队可以延续到下一场。
- **原因**：功能可以被复制，但信任和到场数据会越积越多，不容易复制。

### D4. 信任看得见，但不强制（M8）
- **问题**：强制押金、强制集合点、强制验证，会不会太重？
- **决定**：
  - 默认零门槛；
  - 押金、集合点由发起人自己决定开不开；
  - 签到改成顺手点一下，并计入到场记录；
  - 只有女性专属小队必须认证。

### D5. 不做几百人的大群（M8）
- **决定**：用户可以自己建小队，每队 4–8 人封顶，满了自动开下一队。
- **原因**：研究显示，4 人左右最好聊，5–8 人的聚会体验最好。

### D6. 不做全站广场，热搜只来自组队行为（M9）
- 公开内容只放在每场演出的演出墙（Show wall）里。
- 热搜不接受投放。
- 后来的 D14 在这条基础上加了片段社区。

### D7. Plus One 不卖票（M11）
- **问题**：用户问“Explore 里能找票，那我们的 app 能买票吗？”
- **决定**：不卖票。
  - 原价票跳转到 Ticketmaster 购买。
  - 我们只做粉丝之间多余票的面值转让，小队优先，过户走官方渠道。
  - Explore 去掉“Find a ticket”模式。余票只出现在三个地方：小队聊天、演出页、Tickets 页的 Spares。

## 二、信息架构与页面

### D8. 首页不大改（M11 后）
- 主人对首页满意，写进了 `CLAUDE.md` 的硬性规则：首页只做被明确要求的小改动。
- “Your buddies are going”板块加上后，按主人要求删掉了（v73）。
- 之后首页只动过这几处，都是主人明确要求的：
  - Upcoming 的筛选、无限滚动和动效；
  - Filters 面板；
  - 下拉刷新；
  - 左上角头像。

### D9. Explore 的信息架构（M11）
- **问题**：常驻功能和可以滑走的内容混在一起，热搜也堆在同一页。
- **决定**：
  - 标题、搜索、场景筛选固定在顶部；
  - 热搜挪到二级的 Search 页，点搜索框进入；
  - Explore 只负责找小队。

### D10. Upcoming 的筛选（M11.1 → M13）
- 原来那个排序切换看不懂，去掉了，改成固定按日期排序。
- 时间 chip 加“Filters”按钮（方案 A）。底部面板里可以按演出形式（演唱会、古典、音乐节、连演）、曲风、场馆、只看有余票来筛选，“Show N shows”按钮实时显示结果数量。
- 方案 B 是把所有筛选项铺成一整行，没有采用。

### D11. 接入真实数据（M13）
- 用 Ticketmaster Discovery API 抓了一份 41 场的纽约演出快照。
- API key 绝不进仓库，也不放进发布的页面。
- 新演出的海报直接引用 Ticketmaster 的图片链接，加载失败时显示黑白首字母海报。

### D12. 设计规范统一（M14）
- 以首页为基准建立设计 token：
  - 页面标题 26 号，离顶部 66px；
  - 板块标题 26 号，居中；
  - 圆角只保留 30 / 20 / 18 / 14 / 12 和胶囊形六档。
- 用 `demo/tests/audit_full.py` 自动检查是否偏离规范。完整规范见 `DESIGN.md`。

### D13. 每个元素都要有真功能（M15）
- 导入门票、编辑资料、联系场馆安保、聊天附件、演出墙回复，都从“只弹提示”改成了可以走通的流程。

### D14. Tickets 页维持原设计（M16 前后）
- 按评论要求重排过一次 Tickets 页：票夹置顶、加操作按钮、分摊付款收成一行。
- 主人随即要求恢复，已经完全还原。之后不要再主动重排这一页。

## 三、＋ 菜单（迭代次数最多的一块）

| 版本 | 形式 | 结果 |
|---|---|---|
| v1（M5） | 扇形小卡 | 文字太小、被截断 |
| v2（M16） | 从 ＋ 弹出的扇形卡 | 可以用，但主人希望交互再改 |
| v3（M16.1） | 整行列表 | **被否**：“没有设计感，交互也不有趣了” |
| v4（M16.2） | 一手牌 + 手绘插画 | **被否**：“不够高级，很有 AI 感” |
| v5（M16.3） | 照片卡 | 主人随后给了参考图 |
| v6（M16.4–16.6） | **趣味图形**（参考主人给的图）：黑色大圆 / 转角圆方块 / 波浪星形，标题粗细混排 | ✅ 采用。之后加了自由落体入场（主人要求），悬停效果改得更克制 |

**得到的经验**：
- 主人要的是“有设计感、有趣”的交互，不是信息最高效的列表。
- 真实照片和手绘插画都不对路。
- 主人认可的是“几何图形 + 大字排版 + 物理动效”。

**选项调整（M17.2）**：
- 星星那一项从 Find a +1 改成 Share a clip。
- Find a +1 挪到个人页右上角，名字叫“Open to invites”。

**颜色（待定）**：参考图用的是粉、黄、蓝配米色底，和“只用黑白灰”的规则冲突。彩色版已经写好，但没有启用，等主人决定。

## 四、社区：Clips（M17）

### D15. 做一个社区，让用户分享演唱会片段
- 主人的原话：“其实我是想要社区页面让用户能分享其演唱会的片段的。”
- **入口**：底部导航新增 Clips 标签（主人选的，排在 Home / Explore 之后、Chats 之前）。
- **浏览方式**：全屏竖滑，一次看一条，像 TikTok（主人选的）。
- **和定位的关系**：每条片段都挂着对应的演出和“Find a crew”入口，内容最终服务于组队。

### D16. 头像移出底部导航（M17.1）
- 可选方案有三个：首页左上角、每个主页面右上角、首页顶部问候栏。
- **主人选了首页左上角**。原来的铃铛挪到右上角，和搜索并排。

### D17. 谁可以发帖、评论
- 一开始只允许持票的人评论。主人纠正：“肯定不能只有参加了演唱会的人才能发表评论，最多旁边能打个标签。”
  - → 评论和演出墙回复对所有人开放。去过的人名字旁边标“Was there”，持票的人标“Going”。
- 发片段一开始也要求持票。主人说：“无所谓的，我们这边硬性要带地理位置信息 tag。”
  - → 发片段不再需要持票，但**必须带场馆位置标签**：
    - 视频自带定位时，自动识别并标“On-site”；
    - 没有定位时，必须手动选场馆，标“Tagged”；
    - 不选位置，发布按钮不可用。
  - 演出墙发帖也对所有人开放。

## 五、流程上的约定
- 每次改动都先截图检查，然后发布，再推到 GitHub，并更新 `HANDOFF.md`（同步到 claude.ai 项目）。
- 大改之前先给方案，主人确认后再动手；拿不准的事用选择题问。
- 主人给的参考图，是判断方向的最高依据。
